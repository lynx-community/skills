# Lynx Simulator

With page source and a bundle, an agent can start a local Lynx runtime, prepare the data the page needs, open it, and check the result. Lynx Simulator provides a local client. Its pages use sessions and support the same snapshot, screenshot, and page interaction workflow.

Load the [lynx-simulator Skill](/ai/skills/lynx-simulator) with `agent-lynx skills get lynx-simulator` for page-env authoring and local verification instructions.

## From Page Source to an Inspectable Page

This example uses the public [BankCards example](https://github.com/lynx-family/lynx-examples/tree/3b019cec94b0e7b83e2239dd52839365fdd76522/examples/BankCards). It keeps the original UI and connects the fixed initial amount and card values to `useInitData`. The agent reads that data entry point, writes page-env, and checks what the page actually displays.

Select any of the five steps to change the detail panel. In the second step, select a file to read it; the third step shows the complete `page-env.mjs`. The lines connect test data in page-env to the rendered values and the element refs returned by snapshot.

## What page-env Supplies

`open --page-env` prepares the environment when opening a page. Its fields must match the data structures and bridge methods the page uses.

| Capability           | Field          | Purpose                                                                                                                                        |
| -------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Initial page data    | `templateData` | Supply Lynx initial data, which ReactLynx pages can read through `useInitData`. The example uses it for the amount and card details.           |
| Host properties      | `globalProps`  | Supply configuration read through `lynx.__globalProps`.                                                                                        |
| Native extension data | `nativeData`  | Supply `createContext(nativeData)` when creating each page's native extension contexts.                                                       |
| Bridge call handling | `jsb`          | Return test results based on a bridge method name and its parameters. A function handler can call `next()` to delegate to an existing handler. |

For fixed data, load JSON from a local path, a `file:` URL, or an HTTP(S) URL. For computed or asynchronous data, export a factory from a local `.mjs` or ESM `.js` module. `templateData`, `globalProps`, and `nativeData` can be asynchronous functions; `jsb` can also handle calls asynchronously. Each page evaluates its own environment; relative paths resolve from the CLI's working directory.

After opening the page, continue with [inspection and interaction](page-inspection.mdx) or [logs and runtime values](debugging.mdx). The page's code determines its behavior; page-env supplies the inputs it depends on.

## Startup Options and Extension Packages

`simulator run` selects extension packages and a host version for the whole process. Use `open` to set each page's environment, window dimensions, and rendering mode.

| Option | Behavior and default |
| --- | --- |
| `--ttl <duration>` | Stop this process and its pages after the duration, measured from successful startup. Omit it for no automatic stop time. Accepts `ms`, `s`, `m`, or `h`; bare numbers are milliseconds. |
| `--native-extension <package>` | Add native capabilities such as host elements. Repeat the flag to load multiple npm packages in order. Native binaries must match the OS, architecture, and host version. |
| `--lynxtron-version <version>` | Select an exact Lynxtron version, without ranges or tags. Defaults to the host version pinned by the CLI and does not change the Core version. |

The public CLI prepares `@lynx-js/lynx-simulator-core` and `@lynx-js/lynxtron` from the public npm registry, with no default native-extension packages. Add native capabilities such as host elements with `--native-extension`.

Replace these package and version placeholders with packages published to the public npm registry:

```bash
agent-lynx simulator run --ttl 20m \
  --native-extension '<native-package@version>'
```

`--native-extension` accepts npm names with optional versions, ranges, or tags. Local paths, tarballs, Git URLs, and package subpaths are not accepted. A dependency combination is installed on first use and then cached. Use a new version number after publishing an update; another `run` does not refresh a cached tag.

Native extensions load when the process starts. Supply each page's extension data later through the `nativeData` field of `open --page-env`.

Use `simulator get --client <clientId>` to inspect `coreVersion`, `lynxtronVersion`, `nativeExtensions`, and `logPath`. Package lists contain effective requested specs, not a lockfile of all resolved dependencies. See [Extension usage](https://github.com/lynx-community/skills/blob/release/skills/lynx-simulator/references/extensions.md) and [Package development](https://github.com/lynx-community/skills/blob/release/skills/lynx-simulator/references/extension-development.md) for package contracts and complete examples.

## Manage the Local Runtime

`simulator run` starts an empty runtime and returns a `clientId`. Open a bundle with that ID, select a page from `list-sessions`, and keep the same client and session for subsequent calls.

| Operation                                                             | Purpose                                                                                                           |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `simulator list` / `simulator get --client …`                         | Inspect run status. `get` also returns current sessions.                                                          |
| `simulator logs --client … --follow`                                  | Follow process output, including page-env loading errors.                                                         |
| `simulator stop --client …`                                           | End the selected runtime and its pages. Closing an individual page leaves the runtime available for another page. |
| `simulator run --ttl 20m` / `simulator wait --client … --timeout 20m` | Set an automatic stop time or wait for process exit. A `wait` timeout leaves the process running.                 |

Lynx Simulator uses the daemon connection. The first run prepares dependencies; subsequent runs reuse the local cache. It requires npm and macOS arm64/x64 or Linux x64. Linux also needs the runtime's system graphics libraries. macOS opens a window by default; Linux renders without one. The `open` options `--simulator-window-width`, `--simulator-window-height`, and `--simulator-windowless` control page dimensions and rendering mode.

Use `--simulator-dpr <factor>` to set a positive finite device pixel ratio for windowless rendering. `--simulator-window-background-color '#f5f5f5'` sets the macOS window color behind transparent page areas; windowless mode ignores it. Set the page root's `background-color` to control the background in windowless screenshots.

For the browser DevTool UI, run `agent-lynx inspect --client <clientId> --session <sessionId>` and open the printed localhost URL.
